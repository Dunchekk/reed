# Reed: план продуктового прототипа

Дата: 2026-11-10. Статус: исследование завершено, реализация разрешена владельцем.
Репозиторий: https://github.com/Dunchekk/reed. База: `61a198c`.

## Результат этапа

Нативное iPhone-приложение на SwiftUI с локальной библиотекой, вводом и OCR,
архивом и всеми согласованными фильтрами, Главной, Лентой, историей открытий,
объяснимым подбором карточек и локальными уведомлениями. Первый вход требует
сервера. Backend: TypeScript, Fastify, PostgreSQL; подготовленная интеграция OTP
и отдельный вход для разработки без отправки SMS.

Облачный архив, перенос между режимами, синхронизация устройств, серверный
планировщик и APNs — следующий этап. Не создавать для них фиктивные работающие
переключатели. Виджеты, подписки, почта, серверный OCR, Share Extension,
семантический поиск и сложный импорт также не входят в этот этап.

Критерий завершения: приложение собирается, основные пользовательские сценарии
проверены, тесты проходят, ограниченные или требующие внешних доступов проверки
явно перечислены, история небольших коммитов доступна в рабочей ветке GitHub.
Прототип не означает готовность к публикации в App Store.

## Оценка и критика спецификации

Это проект с умеренным объёмом интерфейса и существенной сложностью поведения.
Основной риск — не CRUD, а история возвращений, планирование, изоляция аккаунтов
и сохранность данных. Число коммитов не является оценкой длительности.

1. **Планирование, выбор и доставка — разные операции.** Успех добавления
   запроса в UserNotifications не означает показ или прочтение. Нужны отдельные
   состояния плана и отдельные события открытия. По неизвестной доставке нельзя
   учить рейтинг или рисовать статистику прочтения.
2. **72 часа нужно проверять относительно времени слота.** Будущие резервации
   также участвуют в проверке. Пересчёт, смена настроек, отмена, повторный запуск
   и явное расписание не должны обнулять историю.
3. **Ограниченный горизонт — продуктовый компромисс.** Локальные уведомления
   можно назначить заранее, но iOS не обещает запуск фонового пересчёта в нужный
   момент. План ограничивается семью днями и консервативным бюджетом очереди;
   при большой частоте эффективный горизонт короче. Интерфейс показывает дату,
   до которой подготовлены возвращения. Бесконечные конкретные возвращения без
   открытия приложения требуют последующего серверного этапа.
4. **Множитель рейтинга не гарантирует частоту.** `×2` — стартовая настройка.
   Результат оценивается длительными воспроизводимыми сценариями; точное обещание
   «ровно вдвое» в интерфейсе не делаем. Охват полного пула важнее фиксированного
   top-N. Каждый пятый автоматический выбор использует отдельный критерий охвата.
5. **FTS движки не идентичны.** Нужен явный контракт токенизации, нормализации,
   префиксного поиска и комбинации фильтров. До облака фиксируем примеры, но не
   добавляем неиспользуемую вторую реализацию поиска или рекомендаций на сервере.
6. **Облачный режим — смена владельца данных, а не простой флаг.** Его нельзя
   незаметно включить в локальный прототип. Границы репозитория, UUID, версии и
   контракт страницы закладываются сейчас; миграционный протокол — позже.
7. **Фото и база не имеют общей транзакции.** Запись файлов должна быть атомарной,
   а незавершённые операции и потерянные ссылки — восстанавливаемыми. Не хранить
   большие изображения в SQLite и не декодировать оригиналы при скролле архива.
8. **Выход, истечение сессии и удаление — разные состояния.** Истечение токена
   не блокирует подтверждённую локальную библиотеку. Явный выход закрывает её и
   отменяет будущие уведомления. Повторный вход того же аккаунта возвращает доступ.
9. **Дизайн не требует копирования макета как картинки.** Сохраняем палитру,
   базовые размеры и композицию, используем нативную навигацию, safe area и
   системные элементы. Не воссоздаём статус-бар и рамку телефона.
10. **Публичный выпуск имеет отдельные условия.** Реальная доставка SMS, проверка
    на физическом iPhone, политика данных, удаление аккаунта, экспорт/восстановление
    и App Review требуют отдельного подтверждённого результата. Локальные тесты
    не подменяют эти проверки.

## Архитектура

### iOS

Один локальный Swift package с отдельными targets закрепляет направление
зависимостей компилятором и позволяет тестировать ядро без симулятора:

```text
ReedApp (SwiftUI, composition root)
  ├─ Features: состояние экрана, события пользователя, навигация
  ├─ Platform: Keychain, URLSession, Vision, Photos/Camera, UserNotifications
  ├─ ReedApplication → ReedDomain
  └─ ReedPersistence → ReedApplication + ReedDomain + GRDB
```

- `ReedDomain`: типы библиотеки, фильтры, правила допуска, расписание, выбор,
  причины, ошибки валидации. Только Swift/Foundation; без UI, БД и сети.
- `ReedApplication`: сценарии, порты хранилища и платформенных сервисов,
  координация сохранения, истории, планирования и доставки. Протоколы вводятся
  на реальных границах; без универсального repository/service/event-bus.
- `ReedPersistence`: миграции, SQL, FTS, транзакции, проекции и наблюдение
  изменений. Domain-модели не становятся GRDB records.
- `ReedApp`: собирает зависимости для текущего аккаунта. Модели экранов на
  `@MainActor`; операции БД, OCR и файлов не выполняют тяжёлую работу на UI-потоке.
- Для простых форм достаточно локального состояния. Модель экрана нужна там,
  где есть загрузка, отмена, ошибка или несколько зависимых действий. Не создавать
  по use-case на каждый getter и по framework на каждый экран.
- Навигация использует типизированные маршруты. Deep link несёт ID, затем
  разрешается через библиотеку текущего аккаунта и показывает unavailable-state.

### Данные

- `Card` — единственное имя основной сущности. UUID создаётся на клиенте.
  Текст обязателен; заголовок, комментарий, источник, страница, папка необязательны.
- `Source`, `Author`, `Tag`, `Folder` — самостоятельные сущности. У источника
  несколько авторов; у карточки несколько тегов и одна папка. При изменении
  источника обновляется поисковый документ связанных карточек.
- `createdAt` и `updatedAt` — технические даты. Редактирование отображаемой даты
  не включаем молча; отдельное поле возможно только при реальном сценарии.
- `Attachment` содержит метаданные и безопасный относительный ключ файла.
  Для каждого аккаунта отдельная БД и каталог файлов, путь основан на UUID.
- Архив читает короткую проекцию. Полный текст и вложения загружаются при открытии.
  Индексы обслуживают фильтры; keyset cursor содержит порядок и уникальный ID.
- FTS-документ нормализуется в одном месте; SQL и FTS-запрос строятся параметрами.
  Изменение карточки и индекса атомарно. Случайная сортировка использует стабильный
  seed запроса и воспроизводимый ключ, а не `ORDER BY random()` на каждой странице.
- Корзина — `deletedAt`, восстановление в течение 7 дней, очистка при доступном
  запуске. Точное фоновое удаление в момент истечения срока не обещаем.

### Возвращения

Поток: `SlotPlanner → ReturnSelector → PlanStore → NotificationDelivery`.
Планировщик не отправляет сообщения, выбор не читает глобальное состояние,
адаптер доставки не выбирает карточку. Время и случайность передаются явно.

1. Строим слоты с учётом локальной календарной даты, часового пояса, выбранных
   дней, окна, дневного лимита и минимального интервала. Индивидуальные события
   занимают лимит первыми; конфликтующие настройки отклоняются с объяснением.
2. Сохраняем выбранное случайное время: повторный расчёт не делает новый розыгрыш.
   У слота стабильная идентичность, у политики — версия. Смена пояса пересчитывает
   только будущее, прошедшая история сохраняется в UTC.
3. Удалённые карточки и запрет возвращения исключены всегда. Для автоматического
   выбора исключены также скрытые, неподходящие по правилам и попадающие в 72 часа.
   Явное событие имеет узкое исключение для фильтров/паузы, а не глобальную отмену
   правил. Скрытая карточка требует отдельного решения для явного возврата.
4. Рейтинг использует давность возврата, ограниченный сигнал ручных открытий и
   явный приоритет. Открытия из уведомления хранятся отдельно. Нет открытия —
   не равно нет интереса; нет доставки — не равно прочитано.
5. Каждый пятый автоматический выбор берёт самую давно ожидающую подходящую
   карточку, начиная с никогда не возвращавшихся. Счётчик фиксируется вместе с
   планом, повторный расчёт не увеличивает его второй раз.
6. Транзакция плана закрепляет выбранную карточку, причину и резервацию. Повторная
   доставка использует тот же ID запроса. Отмена до времени слота освобождает
   резервацию; прошедшая история не переписывается при смене предпочтений.
7. Адаптер сверяет желаемый план с системной очередью и повторяет незавершённую
   синхронизацию после сбоя. История состояний не утверждает доставку без сигнала.
8. «Сегодня» читает сохранённый план. Архив и Лента не создают новые возвращения.

### Backend

Один Fastify-процесс, PostgreSQL и последовательные SQL migrations. Организация
по функциям, внутри функции — transport/application/adapters, когда такое
разделение нужно. Не добавлять микросервисы, Redis, очередь или ORM ради будущего.

- `buildApp(dependencies)` отделён от запуска listener и закрытия ресурсов.
  Это позволяет проверять HTTP через `inject` без настоящего порта.
- OTP provider находится за узким портом. Кандидат — Supabase Auth с SMS provider.
  Проверка доставки на целевые `+7` не доказана и не обещается.
- Локальный development provider явно включается конфигурацией, использует
  синтетические номера/коды и отказывается работать в production. Он не является
  резервным входом, который автоматически включается при ошибке настоящего OTP.
- Серверный аккаунт получает стабильный UUID, связанный с подтверждённым subject
  провайдера. Телефон не служит первичным ключом библиотеки.
- DTO и ошибки валидируются на границе. Есть срок кода, cooldown повторной отправки,
  лимит попыток, обработка истечения и обновления сессии. Секреты и тела auth-запросов
  не логируются. Account ID не принимается от клиента как доказательство доступа.
- В этом этапе сервер хранит аккаунты и необходимые данные входа. Библиотека
  остаётся на iPhone. Не создавать облачную библиотеку с частичной семантикой.

исправляются отдельными короткими коммитами; повторно запускаются затронутые
проверки. До трёх итераций, без бесконечного косметического рефакторинга.

## Минимальная тестовая инфраструктура

- Swift Testing для чистых правил и сценариев; temporary SQLite для persistence.
- Node test runner и Fastify inject; PostgreSQL container для migrations/account.
- Общие JSON fixtures там, где есть договорённость между слоями/языками; без
  общего «универсального» runtime и без тестов, повторяющих каждую строчку кода.
- Небольшое число UI smoke сценариев; не строить большой snapshot framework.
- Время, randomness, OTP HTTP и доставка подменяются на границе. SQLite и
  PostgreSQL в интеграционных проверках настоящие, не mock SQL engine.
- Отдельные сценарии: 72 часа на границе, явное исключение, 500 карточек,
  повторный пересчёт, timezone/DST, queue budget, изоляция аккаунтов, FTS после
  правки метаданных, перезапуск, offline после входа.
- 10k/50k/100k synthetic archive пригодны для измерений. Результаты на Mac или
  simulator не называются измерениями на iPhone; фото/камера и реальная доставка
  окончательно проверяются на физическом устройстве.

## Git и рабочий процесс

Рабочая ветка `reed/implementation`, обычные последовательные commits и push
после проверенных блоков. Никаких amend/force-push опубликованных коммитов,
squash, merge или прямого push в `main` в этом задании. Все осмысленные шаги
остаются видимыми на GitHub. Перед push — diff, проверка затронутого поведения,
проверка staged файлов на случайные данные и подтверждение удалённого SHA.

Настройки Git, если потребуются, только локальные для репозитория. Личные файлы
не исследуются и не меняются. Исходная спецификация на Desktop только читается.
Зависимости и служебные данные инструментов устанавливаются по необходимости,
Docker Desktop исключён. Внешние аккаунты, оплаченные услуги и production не
настраиваются без отдельных доступов/указаний.
