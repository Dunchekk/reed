# Облачная библиотека

`routes` — HTTP-граница: bearer → подтверждённый account, device/epoch headers, проверка входа и лимиты. `CloudDatabase` задаёт общий порядок блокировок account → library; запись изменения и квитанции операции происходит в одной PostgreSQL-транзакции. Это сохраняет порядок cursor и исключает повторное применение operation ID.

`CloudRecords` отвечает за CAS, постоянные tombstones и ссылки. `CloudLibrary` — за страницы неизменяемых изменений и явный сброс epoch. `CloudDevices` — за регистрацию, единственный primary, готовность и отзыв. `media` хранит приватные неизменяемые вложения через заменяемый ObjectStore. Планирование/доставка находятся в соседних `returns` и `notifications`, а не в маршрутах синхронизации.

Сервер не принимает account ID или файловые пути из тела запроса. Удаление карточки не удаляет другую независимую запись, а старый клиент не может воскресить tombstone обычным upsert. Общие правила и JSON описаны в [контракте](../../../contracts/cloud.md).

## Обслуживание и пределы хранения

`CloudMaintenance` запускается при старте и раз в час. Удаление аккаунта сначала блокирует его API, затем удаляет приватные файлы и облачные таблицы, после чего удаляет внешнюю identity. Незавершённый шаг повторяется. Сброс облака атомарно создаёт задание удаления старой epoch; файлы новой библиотеки оно не затрагивает.

История открытий старше 90 дней превращается в tombstone. При явном удалении события и по сроку содержимое стирается также из журнала и квитанций операций, сохраняя последовательности и fingerprint повторов. Это намеренное исключение из неизменяемости payload журнала. Техническая история возвращений остаётся для паузы и порядкового номера выбора.

Сессия загрузки продлевается на 7 дней при обмене. Фото без ссылок из текущих карточек (включая корзину) и без активной загрузки удаляются после 7 дней. Удаление метаданных и задание очистки файла фиксируются раньше физического удаления; повторная загрузка отменяет устаревшее задание. Промежуточные старые версии карточек в журнале не гарантируют доступность прежних фото: клиент завершает pull до скачивания файлов актуальной проекции. Брошенные файлы без SQL-ссылок очищаются с запасом 7 дней.

Технические лимиты прототипа: 2 GiB фото, 512 MiB JSON-записей вместе с журналом/квитанциями, 1000 незавершённых upload sessions, 20 активных устройств. Превышение откатывает SQL-операцию целиком. Журнал/квитанции не обрезаются произвольно: старый cursor и повтор operation ID должны оставаться безопасными. При исчерпании текстовой квоты доступен экспорт и явный сброс облака; платных тарифов нет. Для больших долгоживущих библиотек следующим этапом нужен отдельный контракт компактизации журнала.
